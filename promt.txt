# MASTER PROMPT: Build a Complete Teacher Finding & Tuition Marketplace Website

## 1. YOUR ROLE AND MISSION

Act as a senior full-stack software engineer, UI/UX designer, database architect, security engineer, QA tester, and deployment specialist.

Build a complete, secure, modern, responsive web application called **Teacher Finding Platform**. The platform will connect students and guardians with teachers in Bangladesh.

This must be a real, functional tuition marketplace, not just a static design, landing page, or frontend prototype.

The platform must support:

- Student registration and profile management.
- Teacher registration and profile management.
- Secure authentication and role-based access.
- Tuition requirement posts and teacher availability posts.
- Admin approval for public posts.
- Teacher searching, filtering, and matching.
- Private messaging and price negotiation.
- Booking requests and final Admin confirmation.
- Configurable Student and Teacher commissions.
- Cancellation handling and approved replacement tuition commission waivers.
- Teacher ratings and reviews.
- Payment records and proof verification.
- Complaints, moderation, notifications, and reporting.
- An AI-powered Admin assistant that can interpret instructions, preview proposed changes, and execute authorized changes only after explicit Admin confirmation.
- A secure database, tests, documentation, and deployment through GitHub and Netlify.

**Important:** First inspect the existing project and continue from its current state. Do not delete, replace, or rewrite working code unnecessarily. If the project is empty, create the application from scratch using the recommended architecture below.

Do not stop after generating a plan or mockup. Implement and test the application in phases, using the available tools and the existing project environment.

## 3. CORE PRODUCT REQUIREMENTS

The application should have three distinct roles:

1. Student or Guardian.
2. Teacher.
3. Admin.

A Student and a Teacher may use the same underlying account system, but their permissions, profile sections, dashboards, and available actions must be appropriately separated.

The interface should be easy to understand for users with limited technical knowledge.

Use Bangladesh as the primary market. Display prices in Bangladeshi Taka (BDT/৳) and use the Asia/Dhaka timezone for dates, times, booking windows, and scheduled operations.

Support both Bangla and English interfaces. Users should be able to switch languages, with English as a sensible initial development default. All important navigation, buttons, messages, validation errors, notifications, and status labels must be translatable.

Do not rely on unverified translations, hard-coded dummy records, or misleading statistics in production.

Implement profile data and post data as separate records.

This requirement is critical.

**Option A: For Myself**

- Load the Student's saved profile.
- Automatically populate the relevant form values.
- Let the Student edit the values for this particular tuition post.
- Save the post using its own data snapshot.
- Do not modify the saved Student profile when post fields are edited.

- Show a new form for the other Student or person.

When a Student changes their saved profile later, existing posts should remain unchanged unless the Student explicitly edits those posts.

Provide a preview before publishing or submitting the post.

Apply the same separation principle to Teacher profiles and Teacher availability posts.

## 15. COMMISSION MANAGEMENT — CORE BUSINESS LOGIC

Build a flexible commission engine controlled by Admin settings.

### A. Commission applies to every new tuition

The normal rule is that every genuinely new tuition booking receives its own commission calculation.

Do not charge a monthly recurring commission by default unless Admin explicitly enables that policy.

If a Teacher obtains a new tuition through a separate new booking, evaluate that booking under the applicable commission rules.

Do not accidentally charge the same booking multiple times because of repeated button clicks, page refreshes, retries, or duplicate requests.

### B. Separate Student and Teacher commission

Admin must be able to set Student and Teacher commissions independently.

Examples:

- Student commission: 5%.
- Teacher commission: 8%.
- Student commission: 0%.
- Teacher commission: 10%.
- Both sides free under a promotional rule.

These are examples only, not hard-coded rates.

Provide reasonable configurable commission types, including percentage-based and, if appropriate, fixed-fee commissions.

Validate rate ranges, currency amounts, rounding, and applicable minimum/maximum values.

The Admin must be able to configure whether commission is charged to the Student, the Teacher, or both.

Where both are charged, calculate each side separately from the correct agreed fee and applicable commission base. Display a clear breakdown.

### C. Default rules and customization

Provide:

- Default commission rules.
- Effective dates, if needed.
- Rules for new bookings.
- Optional booking-specific overrides.
- Optional promotional or free-booking rules.
- Separate Student and Teacher rates.
- Commission previews.
- Rule history.
- The ability for Admin to disable or revise a rule.

The ordinary workflow must work without the Admin needing to use AI.

### D. Immutable commission snapshot

At the appropriate final booking-confirmation stage, calculate the commission using the rule applicable to that booking and save a snapshot.

Store:

- Booking ID.
- Agreed tuition fee.
- Commission base.
- Student commission rate and amount.
- Teacher commission rate and amount.
- Rule/version used.
- Payment responsibility.
- Waiver, if applicable.
- Calculation timestamp.
- Final payable amounts.

Existing bookings must not silently inherit new commission rates when the Admin edits the default rules.

If Admin wants to change an existing booking, require a clearly labeled privileged action, an appropriate reason, a recalculation preview, explicit confirmation, and an audit log.

Do not change already-settled financial records silently.

### E. Commission payment tracking

A commission calculation does not prove that money was received.

Track payment states separately, such as:

- Not yet due.
- Due.
- Payment submitted.
- Under verification.
- Paid and verified.
- Failed.
- Cancelled.
- Refunded.
- Waived.

Support payment references and applicable evidence securely.

Prevent unauthorized changes to paid/verified status.

## 16. CANCELLATION, PROOF VERIFICATION, AND ONE FREE REPLACEMENT TUITION

This is an essential business requirement.

The platform must support an Admin-controlled policy under which an eligible cancelled tuition can provide a one-time commission waiver for a replacement/new tuition.

### Intended default policy

If a booking was confirmed, the relevant commission was already paid or financially settled, and the tuition is subsequently cancelled under an eligible circumstance, the affected party must not automatically have to pay the same kind of commission again for one approved replacement tuition.

Instead, the system can grant a one-time replacement commission-waiver credit, subject to Admin review and approval.

**This benefit must not be automatic. The Admin must review the relevant proof first and explicitly approve it.**

### Cancellation process

1. A Student or Teacher submits a cancellation request.
2. They provide the reason and the relevant evidence where required.
3. The other party may be asked for a response or supporting evidence.
4. Admin reviews the request, booking record, payment record, and supporting information.
5. Admin approves or rejects the cancellation request.
6. Admin decides whether a refund, financial adjustment, or replacement waiver is appropriate under the configured policy.
7. The system records the decision and reason.
8. If eligible and approved, a replacement commission-waiver credit is granted.
9. When an eligible replacement booking is confirmed, the system applies that credit instead of charging the applicable commission covered by the waiver.
10. The system marks that credit as used so it cannot be reused.

### Waiver controls

Provide configurable settings for:

- Whether the replacement-waiver policy is enabled.
- Which cancellation reasons qualify.
- Whether the waiver applies to the Student, Teacher, or both.
- The number of replacement credits permitted per eligible cancelled booking.
- Credit expiration, if applicable.
- Whether the waiver covers the full applicable commission or a configured amount.
- Which replacement bookings are eligible.
- Required evidence.
- Whether additional review or escalation is required.

Use a sensible default of one replacement commission waiver for one eligible, Admin-approved cancellation.

A replacement waiver should apply only to its intended future booking and only to the party or parties covered by the Admin decision.

### Prevent abuse

- Require Admin approval.
- Keep a full decision history.
- Prevent duplicate credits for the same cancellation.
- Prevent a credit from being redeemed more than once.
- Prevent users from self-assigning or modifying waiver eligibility.
- Flag repeated or suspicious cancellation patterns.
- Use atomic database transactions or equivalent server-side safeguards when applying a credit.

Do not make refunds automatic merely because a cancellation was requested. Admin must make the applicable refund or adjustment decision and record it.

If commission is still unpaid when an eligible booking is cancelled, apply the configured cancellation policy to void or adjust the outstanding amount appropriately instead of incorrectly recording money as received.

Make the difference clear between a cancellation, a refund, a commission waiver, and a replacement booking. These are separate financial events.

## 20. ADMIN AI AGENT — REQUIRED IN THE INITIAL PRODUCT

Build an AI-powered assistant inside the Admin dashboard.

The AI is an assistant for authorized administrative operations, not an unrestricted owner of the application.

Example prompt from Admin:

"Set the Student commission to 5% and the Teacher commission to 8% for new bookings created during the next seven days. Do not modify existing bookings."

Other examples:

- "Show all booking requests awaiting confirmation."
- "Summarize this week's cancellation requests."
- "Show payment submissions awaiting verification."
- "Preview the commission changes for new bookings next week."
- "Show teachers with verification requests."
- "Summarize unresolved complaints."
- "Find approved bookings whose commission is still unpaid."

### AI capabilities

The assistant should:

1. Interpret the natural-language request.
2. Identify the requested entities, date range, scope, and desired action.
3. Check whether the Admin is authorized for that action.
4. Ask for clarification or return a safe validation error if the instruction is ambiguous or contradictory.
5. Retrieve only data permitted for the current Admin.
6. Prepare a structured proposed action.
7. Display a human-readable preview.
8. Clearly identify which records or future bookings will be affected.
9. Show before-and-after values for relevant settings.
10. Require the Admin to explicitly confirm any consequential change.
11. Execute the action through an authorized, validated server-side operation.
12. Report the actual result.
13. Write an audit record.

### Critical confirmation workflow

Never execute consequential AI-generated changes immediately after interpreting a natural-language prompt.

Use this pattern:

Admin instruction → AI interpretation → scope and validation → preview → explicit Admin confirmation → authorized backend action → result and audit log.

If a request says "new bookings only", preserve existing booking snapshots.

Use explicit date boundaries and the Asia/Dhaka timezone for time-dependent requests.

When the AI cannot determine the intended scope, it must not guess and execute a financial change.

### Secure tool/action architecture

Do not allow the AI to run arbitrary SQL, access secret environment variables, execute arbitrary code, or bypass authorization.

Define a limited set of server-side actions, such as:

- Preview commission-rule changes.
- Apply approved commission-rule changes.
- List pending bookings.
- Retrieve permitted booking summaries.
- List cancellation requests.
- Preview approved cancellation decisions.
- Grant a replacement credit after explicit authorized approval.
- Retrieve payment-verification queues.
- Generate reports from authorized data.

Validate every argument on the server.

Enforce role checks, allowed action types, date ranges, record ownership, transaction consistency, and all applicable business rules.

The AI must not directly fabricate payment status, verification status, reviews, booking consent, or Admin approval.

Sensitive or destructive operations require explicit confirmation and the appropriate permissions even if the natural-language prompt sounds confident.

### AI change log

For each consequential AI-assisted operation, record:

- Admin account.
- Original instruction.
- Structured proposed action.
- Relevant preview or scope.
- Confirmation time.
- Authorized action executed.
- Result.
- Timestamp.
- Failure reason, if any.

Do not store unnecessary personal information or secret credentials in the AI log.

### AI provider and cost

Use a configurable AI provider through a secure server-side API. Never expose an AI API key in frontend source code or browser network responses.

If credentials are not available, implement the full UI and integration interface, document the environment variables and setup instructions, and show a clear unavailable/configuration-required state. Do not fake live AI responses.

The platform's ordinary Admin dashboard must continue to work if the AI service is not configured or becomes unavailable.

## 23. DATABASE ARCHITECTURE

Use PostgreSQL through Supabase unless the existing project already has a compatible, secure database architecture.

Design normalized tables and relationships. Avoid storing all application data in one large profile table.

The schema should cover the following concepts, using appropriate table names and relationships:

- Profiles and trusted role assignments.
- Student-specific profile details.
- Teacher-specific profile details.
- Private contact information.
- Location data or validated location references.
- Subjects and education levels.
- Tuition posts.
- Post subjects and relevant preferences.
- Conversations.
- Conversation participants.
- Messages.
- Offers and counter-offers.
- Bookings.
- Booking terms and consent records.
- Booking status history.
- Commission rules and rule versions.
- Booking commission snapshots.
- Payments and payment evidence.
- Cancellation requests.
- Refunds or adjustments.
- Replacement commission-waiver credits.
- Reviews.
- Complaints and reports.
- Notifications.
- Admin audit logs.
- Protected application settings.

Add suitable foreign keys, constraints, indexes, timestamps, and deletion policies.

Use reliable identifiers and avoid using mutable user-entered strings as database primary keys.

Protect financial history and audit records from unsafe deletion or modification.

### Important data separation

A saved Student or Teacher profile is different from an individual post.

A booking snapshot is different from the current profile and different from current commission settings.

A commission record is different from a payment record.

A cancellation is different from a refund.

A replacement-waiver credit is different from a paid commission.

Represent these concepts explicitly in the schema.

Use appropriate unique constraints to prevent duplicate booking processing, duplicate reviews, and duplicate waiver redemption.

## 24. ROW-LEVEL SECURITY AND BACKEND AUTHORIZATION

Enable and carefully configure PostgreSQL Row-Level Security for tables exposed through Supabase's client-accessible APIs.

Provide tested policies for each table.

Examples of the intended permissions:

- A user can access and edit their own permitted profile fields.
- A user cannot alter their own trusted role or assign themselves Admin.
- Public users can access only approved, public post data.
- Private phone numbers are not exposed through public post or profile queries.
- Only conversation participants can access their conversations and messages.
- Only authorized participants can create valid offers within their conversations.
- Only authorized users can view and act on their bookings.
- Only an authorized backend process or Admin can approve posts, finalize bookings, verify payments, grant waivers, or change commission rules.
- Only eligible Students can submit reviews for completed bookings.
- Only authorized Admins can inspect protected moderation, payment, and administrative records.

Do not use permissive policies that allow an authenticated user to modify their own role field, approval status, commission amount, payment status, or booking confirmation status.

For trusted role assignments, administrative actions, commission calculation, and other privileged changes, use carefully secured server-side functions or equivalent backend mechanisms.

Validate request parameters and enforce authorization on every sensitive operation.

Never rely exclusively on client-side checks.

### Secrets

- Never expose Supabase service-role keys in frontend code.
- Never expose payment secrets or AI API keys in frontend code.
- Store secrets in appropriate server-side environment variables.
- Use the minimum permissions required.
- Document which variables are public and which must remain secret.
- Use safe deployment practices for Netlify environment variables or supported server-side functions.

If Supabase Edge Functions or Netlify Functions are used, make their authorization requirements explicit.
